# Reverse 3D

Input: a finished video (3 to 10 seconds). Longer clips are trimmed to the first 10 seconds. Kling 4.0 Edit allows 3-30 seconds and keeps the input length; 10 seconds is the longest we send. The browser samples up to 12 frames. Gemini names the main subject and the frame. BiRefNet cuts that frame out, Hunyuan3D builds a mesh, and the browser draws gray boxes of the reduced mesh. The run uploads a PNG of the current view as Kling's reference image (`@Image1`).

Output: a blocky Blender-viewport playblast restyle via Kling 4.0 Edit. The side-by-side compare (original left, playblast right) is built in the browser so the graph does not OOM stitching frames. The first frame is dropped on both sides because Kling’s frame 0 is often smeared.

This workflow is playblast-only: LoadVideo → GetVideoComponents → ResizeAndPadImage → CreateVideo (constant 24 fps, original audio) → Kling4EditVideoNode → SaveVideo. LoadImage (node 12) is the browser mesh, wired to `model.reference_images.image_1`. Browser MediaRecorder WebMs often have no duration and confuse LoadVideo into reporting 1 fps; re-wrapping the decoded frames at 24 fps keeps the frame count and satisfies Kling’s 24 fps minimum without stitching (which OOMs).

Kling 4.0 Edit requires both sides between 700 and 4553 pixels and a width/height ratio from 0.40 to 2.50. Node 17 runs on every clip. The server sets its canvas from the file: MP4/MOV sample size, swapped when the track matrix is 90° or 270° so it matches the frames LoadVideo rotates, and WebM PixelWidth/PixelHeight even when the Segment size is the 8-byte unknown length Chrome MediaRecorder writes. It scales uniformly until both sides are at least 700, keeps an already-legal frame as-is up to 1920×1080, and pads with black only when the ratio is outside 0.40–2.50 (smallest legal canvas, 700×1750 or 1750×700). Nothing is cropped or stretched. The long side stays at or under 1920 so a 10 second 24 fps batch does not grow toward Kling’s 4553px ceiling.

## Browser subject

The polygon slider never calls the server. Dragging it rebuilds the subject mesh in the page. Run posts a PNG of that view, as it looks on screen (orbit angle and polygon count), on the existing `POST /api/run/reverse-3d` field `scene`. The server still resizes it and attaches it to node 12.

**Which frame.** Up to 12 frames are taken across the accepted duration (the first 10 seconds) and posted to `POST /api/reverse-3d/subject` with `step=pick`. The graph is `GeminiNodeV3` (`Gemini 3.5 Flash`, thinking `MINIMAL`, 1024 output tokens) with one image slot per frame, then `SaveText`. The reply is read for `frame:` and `subject:` lines. Nothing in the browser scores the pixels. A reply with no frame number is an error, not a fallback.

**The cut-out and the model.** The chosen frame goes through the same BiRefNet chain as background removal: `LoadBackgroundRemovalModel` → `RemoveBackground` → `InvertMask` → `JoinImageWithAlpha` → `SaveImage`. `step=cutout` submits that job to the background-removal deployment (`dep-e45cb437-0991-4689-9f7c-77d5748e3adc`) and returns the job id immediately. The browser polls `GET /api/reverse-3d/subject?cutoutJob=` on this app. That id is not a `/api/jobs/background-removal~…` route, and this app does not start or stop the host. A Comfy API v2 deployment only serves assets and jobs, so `GET /api/object_info` and `GET /object_info/...` answer 404 and the combo cannot be read. When that happens the cut-out still loads `birefnet.safetensors`, the file installed on that deployment. A combo that does come back is used instead, including a different listed name. Reverse 3D (`dep-a166b403-62ba-4598-adeb-708471c20c8c`) is a partner-only Kling release, so its combo for this input is empty and rejects every filename, including `birefnet.safetensors`. When the cut-out image is ready, `step=hunyuan` uploads it and submits `LoadImage` → `TencentImageToModelNode` (Hunyuan3D 3.1, Geometry, 10000 faces) on Reverse 3D. That graph does not contain `LoadBackgroundRemovalModel`. Model 3.1 rejects `LowPoly`. The browser then polls the Reverse 3D job and asks this route to reduce the GLB. About 30% of the faces are kept by clustering vertices. A PNG or any other non-GLB output is an error, not a substitute mesh.

**The mesh.** The reduced mesh is drawn as gray cubes in the page. The slider's right end is that reduced mesh, so 100% is about 30% of the Hunyuan face count, and it is still boxes rather than Hunyuan's LowPoly mode. Dragging left makes the boxes bigger (about 3 to 24 cells along the long side). The label shows the exact triangle count. Nothing is sent to a server for that change. Orbit is a drag on the canvas; Run captures that WebGL view, not the original video and not a placeholder.

**Where it looks wrong.** Gemini can name the wrong person in a crowd, or a frame where the subject is turned away. BiRefNet can leave a halo or eat a limb that matches the background. Hunyuan sees one cut-out, so the back is whatever that one view implies, and the boxes throw away the rest of the surface. A flat product becomes a slab of boxes. The reference still is whatever angle is on screen at Run. A container with no duration and no cluster timestamps is rejected; a file whose timestamps claim a short length is accepted even if the pictures run longer. No paid job is part of the check: mock mode returns a reduced block figure and the two graphs without calling Comfy.
