# Reverse 3D

Input: a finished video (3 to 10 seconds). Longer clips are trimmed to the first 10 seconds. Kling 4.0 Edit allows 3-30 seconds and keeps the input length; 10 seconds is the longest we send. The browser also builds a 3D mesh of one frame and the run uploads a PNG of that mesh as Kling's reference image (`@Image1`).

Output: a blocky Blender-viewport playblast restyle via Kling 4.0 Edit. The side-by-side compare (original left, playblast right) is built in the browser so the graph does not OOM stitching frames. The first frame is dropped on both sides because Kling’s frame 0 is often smeared.

This workflow is playblast-only: LoadVideo → GetVideoComponents → ResizeAndPadImage → CreateVideo (constant 24 fps, original audio) → Kling4EditVideoNode → SaveVideo. LoadImage (node 12) is the browser mesh, wired to `model.reference_images.image_1`. Browser MediaRecorder WebMs often have no duration and confuse LoadVideo into reporting 1 fps; re-wrapping the decoded frames at 24 fps keeps the frame count and satisfies Kling’s 24 fps minimum without stitching (which OOMs).

Kling 4.0 Edit requires both sides between 700 and 4553 pixels and a width/height ratio from 0.40 to 2.50. Node 17 runs on every clip. The server sets its canvas from the file: MP4/MOV sample size, swapped when the track matrix is 90° or 270° so it matches the frames LoadVideo rotates, and WebM PixelWidth/PixelHeight even when the Segment size is the 8-byte unknown length Chrome MediaRecorder writes. It scales uniformly until both sides are at least 700, keeps an already-legal frame as-is up to 1920×1080, and pads with black only when the ratio is outside 0.40–2.50 (smallest legal canvas, 700×1750 or 1750×700). Nothing is cropped or stretched. The long side stays at or under 1920 so a 10 second 24 fps batch does not grow toward Kling’s 4553px ceiling.

## Browser scene

The polygon slider never calls the server. Dragging it rebuilds the mesh in the page. Run posts a PNG of that mesh, as it looks on screen (orbit angle and polygon count), on the existing `POST /api/run/reverse-3d` field `scene`. The server still resizes it and attaches it to node 12.

**Which frame.** Up to 12 frames are taken across the accepted duration (the first 10 seconds). Each frame is drawn down so the long side is 96 pixels. Color is quantized to 4 levels of luma and 4×4 of chroma. Connected regions of the same bucket are flood-filled. Touching regions whose mean colors are within a short RGB distance are merged. A region smaller than 1.2% of the frame is ignored. The frame with the most remaining regions wins. A tie keeps the earlier frame.

**The mesh.** That still becomes a single relief grid. The largest region is the backdrop and stays almost flat, with a slight tilt so an orbit reads as a plane. Every other region is pushed forward, more so toward the bottom of the frame and toward the middle of the region. Vertex colors are the still. The slider picks a triangle budget from 64 to 4096. The grid’s column and row counts are the factor pair closest to that budget and to the frame’s aspect. The label shows the exact triangle count. Orbit is a drag on the canvas; the same projection is what Run captures.

**Where it looks wrong.** This is not a depth model and it does not know what an object is. Flat color, fog, and a subject that matches the wall collapse into one region. Foliage, crowds, confetti, fabric patterns, and scan lines split into extra regions. A cut, a dissolve, or a title card can win because it contains more color boundaries, not because it is the subject. Faces, glass, mirrors, and overlapping objects become blobs. Motion blur and very dark frames flatten. A low polygon count is a coarse version of the same relief, not a new set of boxes. The reference still is whatever angle is on screen at Run, so an orbit that turns the mesh edge-on is what Kling sees. A container with no duration and no cluster timestamps is rejected; a file whose timestamps claim a short length is accepted even if the pictures run longer.
